# Prior art: LLM request routing with fallback, cooldowns, and rate-limit handling (for the `freeai` free-model SDK)

Research date: 2026-11-06. Pages fetched on that date are labeled "current". Older evidence carries its own date. Secondary or SEO sources are labeled "(secondary)" and are not used as the only support for key claims.

## 1. LiteLLM Router: fallbacks, cooldowns, retry policies, routing strategies, shared state, pre-call checks, rate-limit headers, and known pain points

### Takeaway
LiteLLM has the most complete set of knobs (per-exception retry and cooldown policies, three kinds of fallback chains, five routing strategies, Redis-backed shared state, and pre-call context and vision filters). Its 2026 issue tracker also shows how a cooldown layer goes wrong: it benches the only remaining deployment, retries faster than the provider's Retry-After, blames the wrong deployment for a failure, and turns one upstream 429 into a burst of synthetic 429s.

### Cited Findings
**Scope and shared state**
- The Router handles load balancing, queueing, cooldowns, fallbacks, timeouts, and retries (fixed and exponential backoff). "In production, litellm supports using Redis as a way to track cooldown server and usage (managing tpm/rpm limits)." — [LiteLLM Router docs (current)](https://docs.litellm.ai/docs/routing)
- `usage-based-routing-v2` tracks TPM/RPM in Redis with async `redis.incr` and `redis.mget`. The same docs warn that usage-based routing "is not recommended for production due to performance impacts" because the Redis operations add significant latency, and they recommend the default `simple-shuffle`. — [LiteLLM Router docs](https://docs.litellm.ai/docs/routing)

**Routing strategies and knobs**
- The strategies are `simple-shuffle` (the default weighted pick, using a per-deployment `weight`), rate-limit-aware `usage-based-routing-v2` (per-deployment `tpm`/`rpm`), `least-busy`, `latency-based-routing` (`routing_strategy_args`: `ttl` for the latency window, `lowest_latency_buffer` to spread load across near-fastest deployments), and `cost-based-routing` (uses `input_cost_per_token`/`output_cost_per_token`). — [LiteLLM Router docs](https://docs.litellm.ai/docs/routing)
- Newer features: `routing_groups` bind different strategies and args to different model groups in one router, and "session affinity" is a pre-call check that pins every request in a conversation to the deployment that served the first request. — [LiteLLM Router docs](https://docs.litellm.ai/docs/routing)

**Cooldowns**
- Knobs: `allowed_fails` (failures allowed within the window before cooldown) and `cooldown_time` (seconds). Defaults: `allowed_fails` is unset, and `cooldown_time` is 5 s (`DEFAULT_COOLDOWN_TIME_SECONDS`). When `allowed_fails` is unset, a 429 triggers an immediate cooldown, more than 50% failures in the current minute triggers a cooldown, and 401/404/408 trigger a cooldown, each lasting 5 s by default. Once `allowed_fails` is set, 429/401/404 count toward the limit instead of cooling the deployment down at once. — [LiteLLM Router docs (Cooldowns section)](https://docs.litellm.ai/docs/routing)
- Quirk: "Before v1.109.0, the router treated an explicit 3 as unset", because the Admin UI saves the default back on every change. — [LiteLLM Router docs](https://docs.litellm.ai/docs/routing)
- `AllowedFailsPolicy` sets thresholds per exception type: `BadRequestErrorAllowedFails`, `AuthenticationErrorAllowedFails`, `TimeoutErrorAllowedFails`, `RateLimitErrorAllowedFails`, `ContentPolicyViolationErrorAllowedFails`, `InternalServerErrorAllowedFails`, `ServiceUnavailableErrorAllowedFails`, `BadGatewayErrorAllowedFails`, `NotFoundErrorAllowedFails`. A policy set in a deployment's `model_info` takes full precedence over the router-level one, so "a rate-limited third-party endpoint can cool down after its first `RateLimitError`". — [litellm/types/router.py](https://github.com/BerriAI/litellm/blob/main/litellm/types/router.py); [LiteLLM Router docs](https://docs.litellm.ai/docs/routing)
- `disable_cooldowns: True` switches cooldowns off globally. — [LiteLLM config_settings](https://docs.litellm.ai/docs/proxy/config_settings)
- A separate "health check driven routing" page also uses `allowed_fails_policy`: `0` means cool down on the first failure, and `2` means cool down on the third. — [LiteLLM Health Check Driven Routing](https://docs.litellm.ai/docs/proxy/health_check_routing.md)

**Retries**
- `RetryPolicy` sets retries per exception type: `AuthenticationErrorRetries`, `TimeoutErrorRetries`, `RateLimitErrorRetries`, `ContentPolicyViolationErrorRetries`, `BadRequestErrorRetries`, `NotFoundErrorRetries`, `InternalServerErrorRetries`, `ServiceUnavailableErrorRetries`, plus `DefaultRetries`. The most specific field wins, and an unset field defers to the next one, so a policy that sets only `DefaultRetries` also retries 404s unless `NotFoundErrorRetries: 0` is set. RateLimitError gets exponential backoff, and generic errors are retried immediately. — [LiteLLM Router docs](https://docs.litellm.ai/docs/routing); [types/router.py](https://github.com/BerriAI/litellm/blob/main/litellm/types/router.py)

**Fallbacks**
- `fallbacks` (an ordered list per model group, tried after `num_retries`), `default_fallbacks` (used when a group is misconfigured), `content_policy_fallbacks` (for mapped `ContentPolicyViolationError`), `context_window_fallbacks` (for mapped `ContextWindowExceededError`), and `max_fallbacks` (bounds the chain). — [LiteLLM Fallbacks docs (current)](https://docs.litellm.ai/docs/proxy/reliability)
- Within one group, deployments can carry `order: 1/2/...` levels. The docs separate three operations: sibling retry (another deployment at the same order level, within the retry budget), order failover, and cross-group fallback. "Setting `num_retries: 0` disables those retries without disabling order or cross-group failover." A matching `context_window_fallbacks` chain takes priority over later order levels and generic fallbacks, and once it is exhausted the request returns an error. — [LiteLLM Fallbacks docs](https://docs.litellm.ai/docs/proxy/reliability)
- When every deployment in a group is cooling down, a fallback that names a specific `model_info.id` skips the cooldown check. — [LiteLLM Fallbacks docs](https://docs.litellm.ai/docs/proxy/reliability)
- Observability: the response header `x-litellm-model-id` names the deployment that served the request, the header `x-litellm-attempted-fallbacks` is also emitted, and spend logs record `attempted_fallbacks` (int) and `original_model_group`. — [LiteLLM Fallbacks docs](https://docs.litellm.ai/docs/proxy/reliability)
- The proxy re-checks key/team model access and budget for every fallback target. "A zero-cost fallback target is always allowed." — [LiteLLM Fallbacks docs](https://docs.litellm.ai/docs/proxy/reliability)

**Pre-call checks**
- `enable_pre_call_checks: true` is required for context-window enforcement (with an optional `model_info.max_input_tokens` override) and for region filtering. Without it, "requests are sent to the provider regardless of input token count". A separate vision filter is always on: it removes deployments declared text-only (`supports_vision: false`) when the request contains an image, and if every deployment is text-only nothing is removed. — [LiteLLM Fallbacks docs](https://docs.litellm.ai/docs/proxy/reliability)

**Rate-limit headers**
- PR #5355 (Aug 2024) attached provider response headers to mapped exceptions so that router retries could use the OpenAI/Azure `retry-after`. — [litellm PR #5355](https://github.com/BerriAI/litellm/pull/5355)
- Issue #20722: `_time_to_sleep_before_retry` reads `Retry-After` / `x-ratelimit-reset-*` from the exception, but the retry loop passed the *first* exception every time. Against provider Retry-After values of 2 s, 15 s, 30 s, and 60 s, the router slept 9 s in total instead of 107 s (0.08x), which the reporter describes as hammering the API about 12x faster than allowed. The same issue notes that the backoff function returns 0 early when healthy alternative deployments exist, so the bug mainly hits single-deployment or all-in-cooldown setups. A fix was proposed in PR #20725, whose automated review said the added regression test likely fails as written. Merge status not verified. — [litellm #20722](https://github.com/BerriAI/litellm/issues/20722); [PR #20725](https://github.com/BerriAI/litellm/pull/20725)
- Issue #27823 (opened 2026-05-13, closed with fix commits referenced): when LiteLLM itself is the rate limiter ("No deployments available for selected model, Try again in X seconds"), the 429 carried no `Retry-After` header, so clients had to parse the message. The issue cross-references separate work on forwarding the upstream `Retry-After` (#21553) and on exposing a `retry_after` attribute (#26070). — [litellm #27823](https://github.com/BerriAI/litellm/issues/27823)
- PR #40995 changes the error type to `all_deployments_in_cooldown` because client retry logic was treating the cooldown 429 as a server fault. Merge status not verified. — [litellm PR #40995](https://github.com/BerriAI/litellm/pull/40995)

**Documented pain points (2025–2026)**
- One upstream 429 becomes a burst of failures: with one deployment per model and the default ~5 s cooldown, a single upstream 429 put the only deployment in cooldown, and "every request in that window, including every parallel subagent, gets the synthetic 'All deployments ... in cooldown' 429". The fix was `router_settings: { disable_cooldowns: true }` on LiteLLM 1.104.2. — [jimspurgeon/claude-lumo #130 (2026-10-19)](https://github.com/jimspurgeon/claude-lumo/issues/130)
- Lone-deployment lockout: with a router-level `allowed_fails`, a group that had one deployment and no fallback was benched after `allowed_fails + 1` failures. Every call then returned 429 for `cooldown_time` without reaching the provider (the example is a 60 s lockout after two timeouts). The PR keeps a lone deployment warm unless an `allowed_fails_policy` entry names the exception type. It was open as of 2026-10-27, and the same PR references #46182 (an explicit `allowed_fails: 3` treated as unset). — [litellm PR #48644](https://github.com/BerriAI/litellm/pull/48644)
- Caller-caused errors poisoning health: "Caller-supplied request timeout can force primary deployment into cooldown". The fix PR stops counting caller-set timeout 408s toward cooldown. — [litellm #41223](https://github.com/BerriAI/litellm/issues/41223); [PR #41230](https://github.com/BerriAI/litellm/pull/41230)
- Misattributed failures: a mid-stream 429 on `/v1/responses` can be recorded against the fallback deployment that served the retry, depending on thread timing. When all fallback deployments get cooled this way, the fallback group fails with "No deployments available". Reproduced in 14 and 18 of 30 requests on 1.97.0 and in 6 of 30 on the 1.104.0 source. Open as of 2026-10-14. — [litellm #45645](https://github.com/BerriAI/litellm/issues/45645); fix attempt [PR #46073](https://github.com/BerriAI/litellm/pull/46073)
- Free-model 429 hidden in a 200 response (Mar 2025): OpenRouter `:free` rate-limit errors arrived as HTTP 200 with an `error` object (`"Rate limit exceeded: limit_rpd/..."`, `X-RateLimit-Reset` as epoch milliseconds). LiteLLM treated them as an empty reply, so fallbacks never fired. For streaming, "the 200/OK response headers are sent out the door before the headers are received from the remote". Follow-up: PR #10962 "detect and return status codes in streaming responses". — [litellm #9035](https://github.com/BerriAI/litellm/issues/9035)

### Inferences
- The cooldown layer is where bugs concentrate. The reusable rules: (a) never cool the last eligible candidate unless the policy explicitly says so; (b) recompute the wait from the current response's headers on every attempt; (c) key every failure to the exact (provider, model, key) that produced it; (d) exclude caller-caused errors (client timeout, 400, context overflow) from health accounting; (e) when you synthesize an "all cooling" error, include a machine-readable earliest-retry time.
- LiteLLM's three-way split (sibling retry, order failover, cross-group fallback) maps onto freeai's (key, model, provider) structure: retry on another key for an account-level 429, move to another model for a model-level 429 or 404, and move to another provider for 5xx.
- Typed fallback chains (`context_window_fallbacks`, `content_policy_fallbacks`) are cheap to copy as "on error class X, jump to candidate set Y". For example, a context overflow should jump straight to models with a larger `min_context` instead of cooling the current model down.
- Redis on every request is a known latency cost even in LiteLLM. A small library should batch or relax its writes (write-behind, local cache with TTL).

### Gaps
- I did not verify the exact LiteLLM release that contains the #20725, #27823, #40995, and #48644 fixes, or the current status of #21553 (forwarding upstream Retry-After).
- The cap LiteLLM applies to a provider Retry-After (if any) and the exact formula in `_calculate_retry_after` were not confirmed from current source.
- I found no single canonical LiteLLM issue titled "retries amplifying 429s". The amplification evidence is #20722 (retrying too fast) and claude-lumo #130 (cooldown multiplication).

## 2. Other gateways and SDK-level fallback/retry semantics (Portkey, Helicone, Vercel AI Gateway, OpenRouter, Pydantic AI, LangChain, OpenAI SDK, any-llm, aisuite)

### Takeaway
Gateways (Portkey, Vercel, OpenRouter, Helicone) offer ordered fallback lists, status-code filters, capped Retry-After-aware retries, and circuit breakers that fail open. SDK libraries (Pydantic AI, LangChain) offer an ordered model list with a predicate for what triggers fallback, and Pydantic AI adds "response handlers" that reject successful-but-bad responses. None of the SDK-level libraries keeps cooldown or health state across requests. That cross-request memory is freeai's niche.

### Cited Findings
**Portkey (now branded "PRISMA AIRS AI Gateway")**
- Fallback: `{"strategy": {"mode": "fallback", "on_status_codes": [429, 503]}, "targets": [...]}`. By default it triggers on any non-2xx response. Targets nest, so each target can itself be a load balancer, a conditional router, or another fallback. Every attempt in a chain is logged under one Trace ID. — [Portkey Fallbacks (current)](https://portkey.ai/docs/product/ai-gateway/fallbacks)
- Retries: up to 5 `attempts`. Default codes are `[429, 500, 502, 503, 504, 529]`, and `on_status_codes` replaces the defaults. `use_retry_after_headers: true` reads `retry-after-ms`, `x-ms-retry-after-ms`, and `retry-after`. "The cumulative retry wait time for a single request is capped at 60 seconds", and "if any single Retry-After value exceeds 60 seconds, the request will fail immediately". Backoff without headers is 1, 2, 4, 8, 16 s. The response header `x-portkey-retry-attempt-count` is `-1` when retries are exhausted, `0` when none are configured, and `>0` for the attempt that succeeded. Retry attempts are not logged individually. — [Portkey Automatic Retries](https://portkey.ai/docs/product/ai-gateway/automatic-retries)
- Circuit breaker (`cb_config`): `failure_threshold`, `failure_threshold_percentage`, `cooldown_interval` (ms, minimum 30 s), `failure_status_codes` (default >500), and `minimum_requests` (the volume needed before the rate is evaluated). It is tracked per strategy path and closes automatically after `cooldown_interval`. "If all targets are OPEN, circuit breaker is bypassed." — [Portkey Circuit Breaker](https://portkey.ai/docs/product/ai-gateway/circuit-breaker)

**Helicone AI Gateway (Rust, GPLv3, 642 stars)**
- Strategies per the README: model-based latency routing, provider latency-based "P2C + PeakEWMA", weighted distribution, and cost optimization. Rate limits can be set per user, team, or globally by request count, tokens, or dollars. Caching uses Redis or S3. Supports OpenTelemetry logs, metrics, and traces. Integration is a `base_url` swap on the OpenAI SDK. — [Helicone/ai-gateway README](https://github.com/Helicone/ai-gateway)

**Vercel AI Gateway**
- `providerOptions.gateway.models` is an ordered list of fallback models. `order` sets provider preference and can still fall back to other providers. `only` is a hard filter that never fails over outside the list. `sort` takes `'cost'`, `'ttft'`, or `'tps'`. Default provider order is "adjusted for recent provider health". — [Vercel provider options](https://vercel.com/docs/ai-gateway/models-and-providers/provider-options); [Vercel model fallbacks](https://vercel.com/docs/ai-gateway/models-and-providers/model-fallbacks)
- "Any error, such as context limits, unsupported inputs, or provider outages, can trigger a fallback. Requests are billed based on the model that completes successfully." Fallbacks are also pitched for capability mismatches such as multimodal or tool calling. — [Vercel changelog](https://vercel.com/changelog/model-fallbacks-now-available-in-vercel-ai-gateway)
- Through the plain OpenAI SDK, `models` is sent as an extension field, and `completion.model` reports which model actually answered. — [Vercel OpenAI Chat Completions advanced](https://vercel.com/docs/ai-gateway/sdks-and-apis/openai-chat-completions/advanced)

**OpenRouter (server-side routing)**
- `models: [...]` fallback triggers on any error, including context length, moderation, rate limits, and downtime. The request is priced at the model that was ultimately used. "If a `:free` model is followed by a paid model in `models` ... you're billed at the paid model's price. To keep a request free, list only `:free` models." Through the OpenAI SDK, pass `models` in `extra_body`. — [OpenRouter Model Fallbacks (current)](https://openrouter.ai/docs/guides/routing/model-fallbacks)
- The `provider` object accepts `order`, `allow_fallbacks` (default true), `require_parameters`, `data_collection` ("allow"/"deny"), `zdr`, `only`, `ignore`, `quantizations`, `sort` (price/throughput/latency), `preferred_min_throughput`, `preferred_max_latency`, and `max_price`. — [OpenRouter Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection)
- Default routing is weighted-random over providers, scored by effective price, throughput, TTFT, 429 rate, reliability, and well-formed tool calls. "A provider whose errors or 429s are far worse ... gets no traffic until it recovers". "Routing learns how much load each provider can take before it returns 429s". "A burst of 429s or a jump in latency briefly lowers a provider's share". Providers far behind still get a small share "so routing notices when they improve". Conversations stay with one provider while its prompt cache is warm. — [OpenRouter Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection)

**Pydantic AI**
- `FallbackModel(default_model, *fallback_models, fallback_on=(ModelAPIError,))`. `fallback_on` accepts exception types, an exception handler (sync or async), a *response handler* `(ModelResponse) -> bool` that rejects a successful response (for example a truncated reply or a failed native tool call), or a list mixing them. Response handlers apply only to non-streamed requests: a streamed response "accepts the response as is and emits a UserWarning". When all models fail it raises `FallbackExceptionGroup`, whose `.attempts` records every attempt and its usage. — [Pydantic AI FallbackModel API](https://pydantic.dev/docs/ai/api/models/fallback/); [Pydantic AI exceptions](https://pydantic.dev/docs/ai/api/pydantic-ai/exceptions/)
- Error taxonomy: `ModelRateLimitError`, `ModelQuotaExceededError`, `ModelUnavailableError`, `ModelOverloadedError`, `ModelServerError`, `ModelContextWindowExceededError`, `ModelRequestRejectedError`, `ModelAuthenticationError`, `ModelNotFoundError`. `retry_after` is parsed from `retry-after-ms` or `Retry-After`, in both delta-seconds and HTTP-date form. `provider_retry_hint` comes from `x-should-retry`. "OpenRouter uses the `code` of an error inside a 200 response", and an in-stream error "gets the status of the same error before the stream opened, with `in_stream` set". `suggested_model_id` gives a close model name on model-name errors. — [Pydantic AI exceptions](https://pydantic.dev/docs/ai/api/pydantic-ai/exceptions/)
- The default falls back on every category, including context-window overflow, because "a model with a larger context window may accept an input that overflowed another model's". The newer agent-level `ModelFallback` capability defaults to `(ModelAPIError, ContentFilterError)`, so refusals also trigger fallback. — [Pydantic AI models overview](https://pydantic.dev/docs/ai/models/overview/); [Model Fallback capability](https://pydantic.dev/docs/ai/capabilities/model-fallback/index.md)

**LangChain**
- `Runnable.with_fallbacks(fallbacks, exceptions_to_handle=(Exception,), exception_key=None)` tries runnables in order. An exception outside `exceptions_to_handle` is raised immediately, and `exception_key` passes the previous error into the fallback's input. — [langchain_core fallbacks.py](https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/runnables/fallbacks.py)
- LangChain v1 agent middleware: `ModelRetryMiddleware(max_retries=2, retry_on=..., on_failure='continue', backoff_factor=2.0, initial_delay=1.0, max_delay=60.0, jitter=True)` (jitter is ±25%), and `ModelFallbackMiddleware(first_model, *additional_models)`. — [ModelRetryMiddleware ref](https://reference.langchain.com/python/langchain/agents/middleware/model_retry/ModelRetryMiddleware); [ModelFallbackMiddleware ref](https://reference.langchain.com/python/langchain/agents/middleware/model_fallback/ModelFallbackMiddleware)
- "Model-level `with_fallbacks` does not catch refusals, because the middleware detects them after the model call returns." — [LangChain Deep Agents fault tolerance](https://docs.langchain.com/oss/python/deepagents/fault-tolerance)

**OpenAI Python SDK**
- It retries 2 times by default with short exponential backoff on connection errors, 408, 409, 429, and >=500 (`max_retries` configurable, `0` disables). HTTPX2 is now the default HTTP client: the SDK "no longer installs `httpx`", and custom transports "must target HTTPX2's transport interfaces". — [openai-python README](https://github.com/openai/openai-python?tab=readme-ov-file); [openai-python httpx2.md](https://github.com/openai/openai-python/blob/main/httpx2.md)

**any-llm (Mozilla AI) and aisuite**
- any-llm (2,246 stars, created 2025-07-14) offers a unified `completion(model=..., provider=...)` interface and an `AnyLLM.create(...)` class for connection reuse, and documents migration from LiteLLM. Budgets and key management live in a separate "Otari" gateway. The README describes no fallback, retry, or cooldown features. — [mozilla-ai/any-llm](https://github.com/mozilla-ai/any-llm)
- aisuite (16,376 stars) offers OpenAI-style `client.chat.completions.create(model="provider:model", ...)`, an async `acreate`, streaming, and an Agents API. The README describes no fallback or retry features. — [andrewyng/aisuite](https://github.com/andrewyng/aisuite)

### Inferences
- Pydantic AI's response handler is the clearest pattern for free models' "200 OK but useless" failures (empty, truncated, malformed tool call): it lets the user define semantic failure as a predicate. freeai's empty-completion class could generalize to a user-supplied `reject_response(resp) -> bool` hook, limited to non-streamed calls as Pydantic AI does.
- Portkey's caps (60 s cumulative, fail immediately if a single Retry-After exceeds the cap) suit a free-model SDK. A long Retry-After usually means an RPD or daily quota, so the right move is to skip the model and cool it until reset, not to sleep.
- Fail-open when everything is OPEN (Portkey) and an "all cooling" error with retry time (LiteLLM #27823) are the two ways to resolve "every candidate cooled". A free-model SDK should probably fail fast with a typed error carrying `earliest_retry_at` by default, with an opt-in "probe anyway" mode, because blind probing burns scarce RPD.
- Stacked retries: the OpenAI SDK retries 429 twice by default. If freeai ever wraps or proxies the OpenAI SDK, or users put the OpenAI SDK in front of a freeai proxy, the retries multiply. Set the inner `max_retries=0` and document it.
- freeai being on `httpx` while the OpenAI SDK moved to HTTPX2 matters for any "custom transport plugged into the OpenAI SDK" design (see section 6).

### Gaps
- Instructor, Martian, and LlamaIndex were not researched in this pass.
- The Helicone gateway's P2C + PeakEWMA details and cooldown semantics are known only from its README, not from docs or code.
- any-llm and aisuite: I checked only the READMEs, so a lack of fallback features in the README does not prove the features are absent.
- Vercel AI SDK *core* `maxRetries` semantics outside the gateway were not verified.

## 3. Projects built specifically around free LLM APIs (lists, rotators, proxies), 2025–2026

### Takeaway
Since 2025 a crowded set of small "free-tier aggregator" proxies has appeared. Almost all are OpenAI-compatible local servers with virtual model aliases, multi-provider failover, per-key cooldowns, and a dashboard. The better ones add classified cooldowns (minute vs day vs dead model), persistence across restarts, removed-model detection, tool-call verification, privacy filtering, and a "paid guard". The reference list (cheahjs, about 29k stars) shows that free-tier limits come in many dimensions and change often.

### Cited Findings
**Reference list**
- cheahjs/free-llm-api-resources (29,351 stars, current). OpenRouter: "20 requests/minute 50 requests/day Up to 1000 requests/day with $10 lifetime topup", and "Models share a common quota". Google AI Studio: "Data is used for training when used outside of the UK/CH/EEA/EU", with per-model RPM/RPD/TPM (e.g., Gemini 3.6 Flash: 250k TPM, 20 RPD, 5 RPM; Gemma 4 31B: 16k TPM, 14,400 RPD, 30 RPM). Cerebras: 5 RPM, 30k TPM, 1M tokens/hour, 1M tokens/day. Groq: per-model RPD + TPM (Llama 3.3 70B: 1,000 RPD, 12k TPM). Cohere: 20 RPM and 1,000 requests/month. Cloudflare: 10k neurons/day. Kilo Gateway: 200 requests/hour per IP, and "All free models may use your prompts for training". Mistral's free tier "requires opting into data training". The README warns "Please don't abuse these services". — [cheahjs/free-llm-api-resources](https://github.com/cheahjs/free-llm-api-resources)
- Conflicting status reports: FreeRideV3 (checked 2026-10-16) says Cerebras is "trial only: one-time $5, card required, expires after 30 days" and HuggingFace is "PRO only". cheahjs lists both under free providers, with Cerebras per-model limits and "$0.10/month in credits" for HuggingFace. — [Shaivpidadi/FreeRideV3](https://github.com/Shaivpidadi/FreeRideV3); contradicted by [cheahjs](https://github.com/cheahjs/free-llm-api-resources)

**Router and proxy projects**
- waseemnasir2k26/free-llm-router (Node, zero dependencies). OpenAI-compatible with SSE, and virtual aliases `fast`/`smart`/`long-context`. Per-model token buckets for RPM and TPM plus a UTC-day RPD counter. Honors `Retry-After` (seconds or HTTP-date). 5xx/network errors get an exponential cooldown (base 15 s, doubling, 1 h cap). A "model not found / decommissioned" answer marks the model `removed` for a 24 h TTL. A context-window check estimates about 4 chars per token. Paid guard: "Only models with `free: true` are ever called ... There is deliberately no `--paid-ok` flag". Failover happens only before the first byte. Counters, cooldowns, and removals persist to a JSON file. Observability via `/stats`, `/healthz`, and the `x-router-provider`/`x-router-model` headers. Keys are redacted in logs. The server binds to 127.0.0.1 unless `ROUTER_TOKEN` is set. Every limit entry carries a `source` URL and a `last_verified` date (2026-10-12). — [waseemnasir2k26/free-llm-router](https://github.com/waseemnasir2k26/free-llm-router)
- SeyhmusKaya/freellmapi-extended. Health-aware routing "ranked by measured success rate + latency" over 7 days. "Classified cooldowns": per-minute rate limit, per-day quota (waits until UTC midnight), dead route, invalid key. Cascades on 404/429/5xx/timeout/provider-specific 400s. Keyless providers serve as overflow. A daily health probe "diffs upstream catalogs, so dead models are caught before your users hit them". Includes model aliases and an MCP server. — [freellmapi-extended](https://github.com/SeyhmusKaya/freellmapi-extended)
- Shaivpidadi/FreeRideV3. Walks a chain of (provider, key) pairs sorted by recent health. Key-level failures (AUTH, a key-scoped RATE_LIMIT) rotate the key. Model-level failures (MODEL_NOT_FOUND, tier-gated, a model-scoped RATE_LIMIT, TIMEOUT) move to the next model with the same key and "demote the failed pair for a few minutes". QUOTA_EXHAUSTED benches the key and leaves the provider. A coding route is "pinned to models proven to emit correct tool calls". Responses carry the `X-FreeRide-Provider` header. — [FreeRideV3](https://github.com/Shaivpidadi/FreeRideV3)
- devansh-365/freellm. Meta-models `free-fast`/`free-smart`/`free`. Round-robin multi-key with per-key cooldown. Response caching. Rolling 24 h token budget. Circuit breakers. "Strict mode" refuses silent provider substitution. "Privacy routing" skips providers that train on free-tier prompts. Vision-aware routing. Normalizes Gemini/Ollama streaming tool-call bugs. Translates `json_schema` to `guided_json` on NIM. A warning header flags truncated JSON. Sets Gemini `reasoning_effort` "so your max_tokens actually buys you output". — [devansh-365/freellm](https://github.com/devansh-365/freellm)
- tokkkie/free-model-router (2026-04). Dynamic model discovery and priority routing that prefers `qwen`/`nemotron`. Failover on 429, 404, or timeout. "Ghost model detection" applies a 600 s cooldown after a 404. Falls back to local Ollama. "Tool call verification — Automatically tests function calling support on newly detected models and excludes incompatible ones." — [tokkkie/free-model-router](https://github.com/tokkkie/free-model-router)
- kaiser-data/free-llm-proxy-router. Local proxy at `localhost:8080` with "13 routing strategies". Discovers free models by scanning provider APIs. Tracks per-provider reliability. A 5-step chain ends at `openrouter/free`. Gemini gets a 4-dimensional limit check (RPM/TPM/RPD/IPM). A 429 puts the provider on cooldown, "no blocking, no sleep". — [kaiser-data/free-llm-proxy-router](https://github.com/kaiser-data/free-llm-proxy-router)
- alexjm19/free-llm-api-provider. Background pings every 30 s produce health scores. "Sticky provider": once one works, it is reused until it fails. Multi-key. Tier-based routing (`tier-splus` down to `tier-b`), with health overriding tier. — [alexjm19/free-llm-api-provider](https://github.com/alexjm19/free-llm-api-provider/)
- Smaller ones: dklymentiev/free-llm-api-stack (zero-dependency Python, skips providers whose key is unset, raises `NoProviderAvailable`) — [repo](https://github.com/dklymentiev/free-llm-api-stack); bluekap/LLM-Router (FastAPI on LiteLLM, picks the "healthiest" key as least failed and least recently used, SQLite request log) — [repo](https://github.com/bluekap/LLM-Router); jmanzanog/InfiniteLLMFreeTier (round-robin, circuit breaker, `X-Request-ID`) — [repo](https://github.com/jmanzanog/InfiniteLLMFreeTier).
- FreeLLMAPI on HN: a self-hosted gateway pooling free tiers behind one OpenAI-compatible endpoint, with routing, fallback on rate limits, encrypted key storage, and usage tracking, aimed at "personal experimentation and prototyping rather than production". — [HN item 49989006](https://news.ycombinator.com/item?id=49989006)

**OpenRouter's own free router**
- `openrouter/free` "selects a free model at random" among free models after filtering for required features (image input, tool calling, structured outputs). The response `model` field shows which model served the request. — [OpenRouter Free Models Router](https://openrouter.ai/docs/guides/routing/routers/free-models-router)

### Inferences
- The feature set has converged: aliases (`fast`/`smart`/`coding`), classified cooldowns, removed-model TTL, persistence, served-model headers, and a paid guard. freeai already has most of the routing core. Its gaps against this field are persistence, TPM, health ranking, async, and drop-in/proxy, which matches the user's stated "missing" list.
- Differentiators few projects have: per-limit `source` + `last_verified` provenance (waseemnasir2k26), tool-call verification at discovery (tokkkie, FreeRide), and strict mode (freellm).
- Almost every project is a *proxy server*, not an in-process SDK. An in-process library with an optional proxy has less competition.

### Gaps
- Star counts and maintenance activity for most of the small router repos were not captured. Most look like single-author projects of unknown maturity.
- Some FreeLLMAPI details (an `X-Routed-Via` header, up to 20 attempts) came only from a search summary and were not verified on the repo.
- PyPI-specific packages (as opposed to GitHub repos) for free-model auto-selection were not systematically surveyed.

## 4. What developers using free models complain about, and how existing tools respond

### Takeaway
The top complaints are unpredictable 429s (often below the published limits), shared account-wide quotas, errors disguised as HTTP 200 or empty completions, models disappearing without notice, free variants that differ from their paid namesakes, quality below benchmark claims, tool-call unreliability, and prompts being trained on. Tools respond with classified cooldowns, response validation, catalog diffing, tool-call probes, privacy filters, and strict or paid guards.

### Cited Findings
**Rate limits and quota confusion**
- OpenRouter: "Making additional accounts or API keys will not affect your rate limits, as we govern capacity globally". Free-variant RPM/RPD limits apply (the current page renders them as template placeholders). On its own 429s OpenRouter sends `X-RateLimit-Limit`/`-Remaining`/`-Reset`, but "successful inference responses do not include `X-RateLimit-*` headers". `Retry-After` is sent only "when every attempted provider returned a retry hint". A negative credit balance can cause errors "including for free models". `GET /api/v1/key` returns `limit_remaining` and `is_free_tier`. — [OpenRouter Limits (current)](https://openrouter.ai/docs/api/reference/limits)
- Per-model vs account-wide OpenRouter 429s (partial conflict). The current Limits page says "We do however have different rate limits for different models, so you can share the load that way" — [OpenRouter Limits](https://openrouter.ai/docs/api/reference/limits). cheahjs says free "Models share a common quota" — [cheahjs](https://github.com/cheahjs/free-llm-api-resources). The 2025 error bodies show that both kinds exist and that the message text tells them apart: `"Rate limit exceeded: limit_rpd/google/gemini-2.0-flash-thinking-exp-01-21/<uuid>"` (`X-RateLimit-Limit: 80`) and `"limit_rpm/<model>/<uuid>"` (`X-RateLimit-Limit: 4`) are per-model limits — [litellm #9035, Mar 2025](https://github.com/BerriAI/litellm/issues/9035) — while `"Rate limit exceeded: free-models-per-min"` (`X-RateLimit-Limit: 20`, `provider_name: Targon`) is the account-wide free-model limit — [immersive-translate #2725, Apr 2025](https://github.com/immersive-translate/immersive-translate/issues/2725). These message formats are from 2025, and I did not check whether they are still current.
- Changing limits over time: a Mar 2025 issue quotes the OpenRouter docs as "20 requests per minute and 200 requests per day" for `:free` — [litellm #9035](https://github.com/BerriAI/litellm/issues/9035). The current values are 20 RPM, 50 RPD, and 1,000 RPD after $10 lifetime credits — [cheahjs](https://github.com/cheahjs/free-llm-api-resources); [TrueFoundry, 2026-10-08](https://www.truefoundry.com/blog/openrouter-free-models-whats-actually-free-and-what-it-costs-you). TrueFoundry also says "Failed requests can still count against the daily allowance."
- "Constant 429 errors ... I wasn't even close to any published limit", and "OpenRouter pulls free models off the roster without much notice". — [Medium, J. Wadhwa, 2026-07-18](https://medium.com/@jasmeetwadhwa/i-stopped-using-free-models-on-openrouter-b8e7a3c44d05)
- (secondary, a third-party Reddit mirror) Users report `z-ai/glm-5.2:free` rate-limited "even though im literally not even using it", and Gemma 429s with a 16k context cap despite 1,000 RPD. — [Reddit snapshot via sentinel mirror, 2026-08](https://reddit.sentinel-team.org/posts/1vwmy64/snapshots/2026-08-26T21%3A06%3A32.032085Z)
- (secondary) Agents are "disproportionately hit because retries-on-429 create feedback loops". Suggested mitigation: cap retry concurrency to 1 with exponential backoff. — [standardcompute.com](https://standardcompute.com/fix/openrouter-rate-limited)

**Errors disguised as success or empty output**
- Apr 2025: an OpenRouter free model returned HTTP 200 with `{"error": {"message": "Rate limit exceeded: free-models-per-min", "code": 429, ... "provider_name": "Targon"}}`, and the client saw only `completion_tokens = 0`. — [immersive-translate #2725](https://github.com/immersive-translate/immersive-translate/issues/2725); same pattern in [litellm #9035](https://github.com/BerriAI/litellm/issues/9035)
- Mid-stream limits "arrive as an SSE event with `finish_reason: "error"` instead of an HTTP 429". — [OpenRouter Limits](https://openrouter.ai/docs/api/reference/limits)
- Causes of "no content generated": cold start, scaling, or "a reasoning model spent the whole `max_tokens` budget on reasoning", which returns a 200 with `finish_reason: "length"`, empty content, and `reasoning_tokens` close to `completion_tokens`. In that case "Retrying does not help; raise `max_tokens` or cap reasoning instead." The error-type table lists `rate_limit_exceeded` (429), `provider_overloaded` (503), and `provider_unavailable` (502, "invalid or empty response"). — [OpenRouter Errors and Debugging](https://openrouter.ai/docs/api_reference/errors-and-debugging)

**Model churn, single hosts, and variant differences**
- On 5 Oct 2026 there were 19 free text models. "Every one of the 19 free models has exactly one endpoint ... when it's busy or down there's nowhere to fall back to." The median free model had been listed for 75 days, and 8 of 19 appeared in the previous 60 days. Previously recommended IDs such as `qwen/qwen3-coder:free` have disappeared. A free variant can differ from the paid one: Gemma 4 31B's free endpoint caps output at 32,768 tokens versus up to 262,141 on paid hosts. One-day uptime was mostly 97–100%, with an 86% outlier. — [TrueFoundry, 2026-10-08/15](https://www.truefoundry.com/blog/openrouter-free-models-whats-actually-free-and-what-it-costs-you)

**Privacy and prompt training**
- 9 of 19 free models run on hosts whose policy "may train" on prompts. Turning off "free endpoints that may train" makes those 9 unavailable rather than rerouting them. Data-policy-based routing is listed as a Standard-plan feature, not part of the Free plan. Requests can set `data_collection: "deny"`. — [TrueFoundry](https://www.truefoundry.com/blog/openrouter-free-models-whats-actually-free-and-what-it-costs-you); `data_collection` field in [OpenRouter Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection)
- Google AI Studio's free tier trains on data outside UK/CH/EEA/EU, Mistral's free tier requires opting into training, and Kilo's free models may train. — [cheahjs](https://github.com/cheahjs/free-llm-api-resources)

**Quality and tool calling**
- Free models near the top of SWE-bench produced "code that looked plausible on the surface but broke on the first real test". — [Medium, 2026-07-18](https://medium.com/@jasmeetwadhwa/i-stopped-using-free-models-on-openrouter-b8e7a3c44d05)
- OpenRouter's "Exacto" exists because "tool-use propensity and accuracy vary between providers significantly more than the standard benchmarking would suggest". It reports a 10–20% gain on Tau2Bench/LiveMCPBench over default routing (self-reported) and attributes the variance mostly to tool-call parsers, not quantization. — [OpenRouter: Provider Variance, Introducing Exacto](https://openrouter.ai/blog/announcements/provider-variance-introducing-exacto/)
- Tool responses: tokkkie probes function calling on newly discovered models, FreeRide pins coding traffic to "models proven to emit correct tool calls", freellm normalizes streaming tool-call bugs, and OpenRouter's endpoint metadata exposes `supportsToolChoice` per variant ("`tool_choice` in `supported_parameters` only says the parameter is accepted; these flags say which of its values passed testing"). — [tokkkie](https://github.com/tokkkie/free-model-router); [FreeRideV3](https://github.com/Shaivpidadi/FreeRideV3); [freellm](https://github.com/devansh-365/freellm); [OpenRouter PublicEndpoint](https://openrouter.ai/docs/client-sdks/typescript/models/publicendpoint)

### Inferences
- OpenRouter's statement that more keys or accounts do not raise limits means multi-key rotation for OpenRouter is pointless and against the spirit of the terms.
- freeai's model-level vs account-level 429 split should read the OpenRouter error message prefix, both on HTTP 429s and on 429s embedded in 200 bodies. `limit_rpm/<model>/...` and `limit_rpd/<model>/...` should cool only that model, with `limit_rpd` lasting until `X-RateLimit-Reset`. `free-models-per-min` (and any equivalent account-wide daily message) should cool every `:free` candidate on that account. Upstream provider 429s (`error.metadata.provider_code` present) should cool only that model/provider. Treat unknown message shapes conservatively as model-level with a short cooldown, and log them so the classifier can be updated, because these formats date from 2025 and may have changed.
- freeai's existing "empty completion" class needs two sub-cases: (a) transient or provider-side (cold start, hidden 429), which should fail over and cool down; (b) reasoning budget exhausted (`finish_reason="length"` with reasoning tokens close to completion tokens), which should not cool the model but should raise or adjust `max_tokens`/reasoning effort.
- Because free models usually have exactly one host, provider-level fallback inside OpenRouter does not help them. Model-level failover across providers (OpenRouter to Groq/Gemini/Cerebras) is the only real redundancy.

### Gaps
- I could not retrieve HN comment threads (the item page showed only the submission) or primary Reddit threads. Reddit evidence here comes from a third-party mirror.
- The official OpenRouter privacy/logging docs page was not fetched directly. The privacy claims rest on TrueFoundry's dated analysis.
- I found no quantitative survey ranking complaint frequency. The ordering above is a qualitative synthesis.

## 5. Model-quality selection approaches usable programmatically

### Takeaway
Cheap, programmatic quality signals exist: the Artificial Analysis free API (benchmarks, speed, and price for 1,000 requests/day), the LMArena leaderboard dataset on Hugging Face, and OpenRouter's per-endpoint uptime, latency, throughput, and tool-choice metadata. Learned routers (RouteLLM, Not Diamond RoRF) need a fixed model pair and an eval set, which does not fit a model pool that changes every few weeks. User-defined tiers and aliases plus light startup probes are the common pragmatic choice in free-model projects.

### Cited Findings
- Artificial Analysis free API: `GET https://artificialanalysis.ai/api/v2/data/llms/models` with header `x-api-key`. It returns `evaluations` (e.g., `artificial_analysis_intelligence_index`, `artificial_analysis_coding_index`, `artificial_analysis_math_index`, `mmlu_pro`, `gpqa`, `hle`, `livecodebench`), `pricing`, `median_output_tokens_per_second`, and `median_time_to_first_token_seconds`. "Rate-limited to 1,000 requests per day", "Attribution is required", and "please do not include in client side code and cache responses". Use stable `id`s, because slugs and names may change. — [Artificial Analysis API docs](https://artificialanalysis.ai/documentation)
- LMArena: the full leaderboard history is published as a public dataset `lmarena-ai/leaderboard-dataset` (14 subsets covering 10 arenas, with `latest` and `full` splits, as parquet). No documented REST API was found. — [Arena Leaderboard Dataset blog](https://arena.ai/blog/arena-leaderboard-dataset/); [HF dataset files](https://huggingface.co/datasets/lmarena-ai/leaderboard-dataset/tree/0e5b8bd9ba5ae68481a4939040b93ea2f3db8c8a/image_edit)
- OpenRouter endpoint stats: `GET /api/v1/models/{author}/{slug}/endpoints` returns per-endpoint `uptime_last_5m`/`_30m`/`_1d`, `latency_last_30m` (p50–p99, TTFT, "Only visible when authenticated"), `throughput_last_30m`, `supported_parameters`, `supportsToolChoice`, `status`, `context_length`, `max_completion_tokens`, `quantization`, and `pricing`. Uptime is "the share of minutes in which at least 80% of provider attempts succeeded, counting only minutes with 10 or more attempts. Rate-limited and caller-caused failures are excluded. Null when no minute had enough traffic." — [OpenRouter list endpoints](https://openrouter.ai/docs/api/api-reference/endpoints/list-all-endpoints-for-a-model); [PublicEndpoint schema](https://openrouter.ai/docs/client-sdks/typescript/models/publicendpoint)
- OpenRouter `:exacto` is a quality-first provider sort for tool calling. — [Exacto blog](https://openrouter.ai/blog/announcements/provider-variance-introducing-exacto/)
- RouteLLM (LMSYS) provides a "drop-in replacement for OpenAI's client (or launch an OpenAI-compatible server)". Its routers are `mf` (matrix factorization, recommended), `sw_ranking` (weighted Elo), `bert`, `causal_llm`, and `random`. They route between one strong and one weak model with a per-request cost threshold and were trained on the `gpt-4-1106-preview`/`mixtral-8x7b` pair. The project claims "reduce costs by up to 85% while maintaining 95% GPT-4 performance" on MT Bench. — [lm-sys/RouteLLM](https://github.com/lm-sys/RouteLLM/)
- Not Diamond RoRF: random-forest routers with 12 pre-trained routers across 6 model pairs and a `threshold` parameter. It reuses RouteLLM's Controller. — [Not-Diamond/RoRF](https://github.com/Not-Diamond/RoRF/)
- Heuristic approaches in free routers: user-tier routing with health overriding tier (alexjm19), meta-model aliases (freellm, waseemnasir2k26), name-pattern priority (tokkkie's `qwen`/`nemotron`), a measured 7-day success and latency rank (freellmapi-extended), and "health × popularity" (FreeRideV3). — [alexjm19](https://github.com/alexjm19/free-llm-api-provider/); [freellm](https://github.com/devansh-365/freellm); [tokkkie](https://github.com/tokkkie/free-model-router); [freellmapi-extended](https://github.com/SeyhmusKaya/freellmapi-extended); [FreeRideV3](https://github.com/Shaivpidadi/FreeRideV3)
- Startup or periodic probes: tool-call verification on discovery (tokkkie), a daily health probe plus catalog diff (freellmapi-extended), and a 10 s reliability analysis via `--fiable` (alexjm19). — sources as above

### Inferences
- For freeai: user-defined tiers and glob `prefer` lists (already present) plus an optional quality-score enrichment hook. Map OpenRouter IDs to Artificial Analysis IDs through a user-overridable table, cache it on disk for at least a day, and credit Artificial Analysis. This gives quality ranking without bundling volatile data.
- Live health ranking can be seeded from OpenRouter endpoint uptime and latency at discovery time and then updated with local EWMA success and latency. OpenRouter's uptime excludes rate-limited failures, so it measures provider health, not quota headroom. freeai still needs its own 429 tracking.
- Learned routers are a poor fit for a small free-model library: their pairs are fixed, they need retraining, and the free pool churns on a median 75-day lifetime (section 4).

### Gaps
- Two secondary blogs claim that `openrouter/auto` runs on Not Diamond and that a `cost_quality_tradeoff` knob exists (0–10, default 7), but no primary OpenRouter doc confirmed either here. Both are unverified. — (secondary) [menuagentic](https://menuagentic.com/blogs/routellm-vs-not-diamond-vs-vllm-semantic-router-vs-openrouter-auto/); [seangeng.com](https://seangeng.com/writing/the-honest-guide-to-llm-routing)
- I did not check whether OpenRouter exposes its public "rankings" (token-share leaderboards) through a documented API.
- Martian's routing API was not researched.
- No source describes how well Artificial Analysis or LMArena cover the specific free variants. The TrueFoundry finding that free variants can differ from paid ones means scores for the paid model may not transfer.

## 6. Drop-in compatibility patterns (OpenAI-compatible proxy, OpenAI-client mimic, framework integrations) and observability hooks

### Takeaway
There are three established patterns. (1) A local OpenAI-compatible server (`/v1/chat/completions`, `/v1/models`) that any OpenAI SDK reaches by changing `base_url`: LiteLLM proxy, Helicone, nearly every free router, and RouteLLM all take this route. (2) An in-process object that mimics `client.chat.completions.create`: aisuite and RouteLLM's controller. (3) Framework adapters: Pydantic AI accepts any OpenAI-compatible endpoint through `OpenAIChatModel` plus a custom Provider, or through a custom `Model` subclass; LangChain composes with `with_fallbacks`. For observability, the OpenTelemetry GenAI semantic conventions are the neutral target.

### Cited Findings
- LiteLLM proxy usage: `openai.OpenAI(api_key="anything", base_url="http://0.0.0.0:4000")`, and served-deployment info is read from response headers through `with_raw_response`. — [LiteLLM Fallbacks docs](https://docs.litellm.ai/docs/proxy/reliability)
- Helicone migration is a diff of `base_url` and an `openai/<model>` model name. — [Helicone/ai-gateway](https://github.com/Helicone/ai-gateway)
- OpenRouter extensions go through `extra_body={"models": [...]}` in the OpenAI SDK. — [OpenRouter Model Fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks)
- The OpenAI SDK accepts `http_client=DefaultHttpx2Client(transport=...)` and `with_options(...)` for per-request overrides. HTTPX2 is now the default, and "custom transport subclasses, mounted transports ... must target HTTPX2's transport interfaces". `openai` no longer installs `httpx` transitively. — [openai-python README](https://github.com/openai/openai-python?tab=readme-ov-file); [httpx2.md](https://github.com/openai/openai-python/blob/main/httpx2.md)
- aisuite mimics the OpenAI client shape: `client.chat.completions.create(model="openai:gpt-4o", ...)`, with `acreate` for async and OpenAI-shaped stream chunks. — [aisuite](https://github.com/andrewyng/aisuite)
- RouteLLM ships both a drop-in OpenAI client and an OpenAI-compatible server. — [RouteLLM](https://github.com/lm-sys/RouteLLM/)
- Pydantic AI: "If a model API is compatible with the OpenAI API, you do not need a custom model class and can provide your own custom provider instead". Otherwise subclass `Model` and `StreamedResponse`. Its OpenAI-compatible provider list already includes LiteLLM and Vercel AI Gateway. — [Pydantic AI models overview](https://ai.pydantic.dev/models/overview/)
- Free-router proxies expose `/v1/chat/completions` (JSON + SSE) and `/v1/models`, plus served-model headers (`x-router-provider`, `x-router-model`, `X-FreeRide-Provider`), and default to safe binds (127.0.0.1 unless a token is set). — [waseemnasir2k26](https://github.com/waseemnasir2k26/free-llm-router); [FreeRideV3](https://github.com/Shaivpidadi/FreeRideV3)
- OpenTelemetry GenAI spans: `gen_ai.provider.name` (required), `gen_ai.request.model`, and `gen_ai.response.model` (recommended, may be more specific than the request), with span name `{gen_ai.operation.name} {gen_ai.request.model}`. A metrics spec also exists. — [OTel GenAI spans](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-spans); [OTel GenAI metrics](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-metrics/)
- Shared or persistent state building blocks: `pyrate-limiter` supports multiple rates on one key (e.g., 5/s and 1000/h), sliding-window-log, fixed-window, and GCRA/token-bucket algorithms, and InMemory, SQLite (`use_file_lock=True` for multi-process on one host), Redis (sync and async), Postgres, and multiprocessing backends. SQLiteBucket is sync-only, and the table offers `BucketAsyncWrapper` "to make any sync bucket async-safe". It warns that RedisBucket keeps one sorted-set member per consumed unit, which grows large for daily quotas. `limits` supports memory, memcached, and Redis storage with fixed, moving, and sliding-window-counter strategies, plus async storages. — [pyrate-limiter on PyPI](https://pypi.org/project/pyrate-limiter/); [limits quickstart](https://limits.readthedocs.io/en/latest/quickstart.html); [limits custom storage](https://limits.readthedocs.io/en/stable/custom-storage.html)

### Inferences
- The cheapest high-value drop-in for freeai is an in-process `client.chat.completions.create(...)` facade that returns OpenAI-shaped objects, in the style of aisuite. An optional `freeai serve` proxy (`/v1/chat/completions`, `/v1/models`, served-model and attempt headers, 127.0.0.1 bind by default, optional bearer token) then unlocks every OpenAI-compatible tool and framework, including Pydantic AI and LangChain, without writing per-framework adapters.
- A custom httpx transport injected into the OpenAI SDK is fragile: the SDK has moved to HTTPX2 while freeai uses `httpx`. A facade or proxy avoids coupling to SDK transport internals.
- Observability: map the existing `on_attempt` callback to OTel GenAI span attributes in an optional extra (`freeai[otel]`), with one span per attempt carrying `gen_ai.provider.name`, `gen_ai.request.model`, and `gen_ai.response.model`, plus custom `freeai.attempt.*` / `freeai.failure_class` attributes. This also covers Langfuse and Logfire, which ingest OTel.
- For cross-process state, a single-host SQLite store (WAL plus file lock) holding cooldowns, RPD/TPD counters, removed models, and health EWMA fits most free-model users. Redis is for multi-host deployments. pyrate-limiter already provides multi-window, SQLite/Redis, and sync/async, which saves writing a limiter. Its Redis memory warning for daily windows argues for counter-based RPD/TPD.

### Gaps
- No verified evidence on how the LlamaIndex `OpenAILike` and LangChain `ChatOpenAI(base_url=...)` integrations behave with routers that change the served model mid-session (e.g., the `model` field differs from the request).
- I did not confirm whether `gen_ai.provider.name` replaced `gen_ai.system` in semconv v1.37.0. Only a secondary source says so.
- License and maintenance review of pyrate-limiter and limits was not done. Both would be new runtime dependencies, and the project rules require a dependency justification before adding them.

## 7. Prioritized features and design lessons for `freeai` (user value vs implementation cost)

### Takeaway
The highest-value, lowest-cost work is making failure handling *correct* rather than adding features: detect errors hidden in 200 responses and streams, compute waits from each response, classify cooldowns by limit window, never silently bench the last candidate, split "empty completion" into its causes, and add a free-only guard. Next come async, persistent state, TPM limits, and health ranking. Drop-in facade or proxy and OTel come after that. Learned quality routers should be avoided.

### Cited Findings
- Hidden errors in 200 bodies and SSE error chunks are a recurring free-model failure — [litellm #9035](https://github.com/BerriAI/litellm/issues/9035); [immersive-translate #2725](https://github.com/immersive-translate/immersive-translate/issues/2725); [OpenRouter Limits](https://openrouter.ai/docs/api/reference/limits); [Pydantic AI `in_stream`](https://pydantic.dev/docs/ai/api/pydantic-ai/exceptions/)
- Per-attempt Retry-After matters: a stale value meant retrying 12x faster than allowed — [litellm #20722](https://github.com/BerriAI/litellm/issues/20722). Cap total wait and fail fast on long Retry-After — [Portkey retries](https://portkey.ai/docs/product/ai-gateway/automatic-retries)
- Lone-candidate and all-cooling failure modes — [claude-lumo #130](https://github.com/jimspurgeon/claude-lumo/issues/130); [litellm PR #48644](https://github.com/BerriAI/litellm/pull/48644); [litellm #27823](https://github.com/BerriAI/litellm/issues/27823); [Portkey circuit breaker bypass](https://portkey.ai/docs/product/ai-gateway/circuit-breaker)
- Classified cooldowns by limit window — [freellmapi-extended](https://github.com/SeyhmusKaya/freellmapi-extended); [waseemnasir2k26](https://github.com/waseemnasir2k26/free-llm-router); [FreeRideV3](https://github.com/Shaivpidadi/FreeRideV3)
- Reasoning-budget empty responses should not be retried — [OpenRouter Errors](https://openrouter.ai/docs/api_reference/errors-and-debugging)
- Paid fallthrough risk — [OpenRouter Model Fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks); paid guard pattern — [waseemnasir2k26](https://github.com/waseemnasir2k26/free-llm-router)
- Misattribution and caller-caused cooldowns — [litellm #45645](https://github.com/BerriAI/litellm/issues/45645); [litellm #41223](https://github.com/BerriAI/litellm/issues/41223)
- OpenRouter quota is global per account, so key rotation does not help — [OpenRouter Limits](https://openrouter.ai/docs/api/reference/limits)

### Inferences
Ranked list. The score is user value (H/M/L) against cost for a small library (L/M/H). "Already" marks parts freeai has.

**P0: high value, low cost (correctness fixes and cheap wins)**
1. **Detect errors hidden in 200 bodies and stream chunks.** Parse `{"error": {...}}` in 200 JSON bodies and in SSE chunks (`error` field or `finish_reason: "error"`), and map the embedded `code` (429/502/503) into the existing failure classes. Before the first token, fail over. After the first token, raise a typed `MidStreamError` with the classification and still record the cooldown against the correct candidate. (Value H, cost L.)
2. **Wait time from every response, with caps.** Parse `retry-after-ms`, `Retry-After` (seconds and HTTP-date), and `X-RateLimit-Reset` (OpenRouter uses epoch **ms**), freshly on each attempt. Add `max_wait_per_attempt` and `max_total_wait` budgets (Portkey uses 60 s). If the wait exceeds the budget, cool the candidate until the reset and move on instead of sleeping. (H, L.)
3. **Cooldown by limit window.** Distinguish RPM (seconds), RPD/TPD (until `X-RateLimit-Reset` or the next UTC midnight; persist this), removed or 404 model (TTL around 24 h plus catalog refresh), and key/account-level limits (401/402/negative balance bench the key; an OpenRouter account-wide `free-models-per-min`-style 429 cools *all* `:free` models on that account, while `limit_rpm/<model>` and `limit_rpd/<model>` cool only that model; see section 4). freeai already separates model-level from account-level 429; the missing pieces are the daily window and keying the split off the OpenRouter message prefix. (H, L.)
4. **Last-candidate and all-cooling semantics.** Never let a plain failure-count threshold bench the only eligible candidate. When everything is cooling, raise `AllCandidatesCoolingDown(earliest_retry_at=..., per_candidate=...)` by default, with an opt-in `probe_when_all_cooling=True` (the Portkey fail-open behavior). (H, L.)
5. **Split "empty completion".** (a) `finish_reason="length"` with reasoning tokens close to completion tokens is not a provider fault: do not cool down, and surface a hint to raise `max_tokens` or lower reasoning effort (freellm sets Gemini `reasoning_effort` for this reason). (b) A truly empty 200 is a transient fault: fail over and apply a short cooldown. Also add a user `reject_response` predicate in the style of Pydantic AI response handlers, for non-streamed calls only. (H, L.)
6. **Free-only guard on by default.** Refuse candidates whose pricing is not $0, never send OpenRouter `models[]` mixes containing paid IDs, and require an explicit `allow_paid=True` opt-in. (H, L.)
7. **Keep caller-caused errors out of health.** Client-side timeouts, 400 schema errors, and context overflow do not count toward cooldown or health. Context overflow should instead jump to candidates with enough context (the typed-fallback idea from LiteLLM `context_window_fallbacks` and Pydantic AI). Key every attempt record to the exact (provider, model, key). (H, L.)
8. **Served-model metadata on every result.** Report `served_provider`, `served_model`, `attempts`, `total_wait_s`, and `fallback_reason` on the response object. freeai already has attempt logs, so this exposes them the way LiteLLM `x-litellm-model-id`/`attempted_fallbacks` and Portkey `x-portkey-retry-attempt-count` do. Add a strict mode that raises instead of substituting a different model (freellm). (M-H, L.)
9. **Retry budget hygiene.** One global attempt cap per request plus jitter (LangChain uses ±25%), and documentation telling users to set inner OpenAI SDK `max_retries=0` to avoid multiplied retries. (M, L.)

**P1: high value, medium cost (the user's stated gaps)**
10. **Async API.** An `AsyncClient` mirror on `httpx.AsyncClient`. Factor routing, classification, and cooldown into a sans-IO core shared by sync and async so the semantics cannot drift. Every comparable library ships both (LiteLLM `acompletion`, aisuite `acreate`, pyrate-limiter sync and async). (H, M.)
11. **Persistent and shared state.** A pluggable `StateStore` with `memory` (default), `sqlite` (single host, multi-process, WAL and file lock), and optional `redis`. It persists cooldowns, RPD/TPD counters, removed models, and health stats. waseemnasir2k26 proves the value of a JSON file. LiteLLM's Redis latency warning argues for write-behind or batching. Consider pyrate-limiter for the limiter rather than writing one (pending a dependency review). Its SQLite backend is sync-only and needs `BucketAsyncWrapper` (or a thread offload) under the async API. (H, M.)
12. **TPM/TPD limits.** Estimate tokens before the call (about 4 chars per token, or a tokenizer if one is available), reserve them against token buckets, and reconcile with `usage` after the response. Support many windows per candidate (RPM, RPD, TPM, TPD, tokens/hour, monthly), since Cerebras, Gemini, Groq, and Cohere all mix these windows. Store limit provenance (`source`, `last_verified`) in the style of waseemnasir2k26. (H, M.)
13. **Health-based ranking.** A per-candidate EWMA of success rate and TTFT/latency with time decay. Seed it from OpenRouter endpoint `uptime_last_30m`/`latency_last_30m` (latency needs auth). Choose with power-of-two-choices (Helicone P2C) or weighted-random rather than strict best-first to avoid herding, and keep a small exploration share as OpenRouter does. Expose it as `strategy="health"` next to the existing priority/round_robin/random. (H, M.)
14. **Capability verification probes.** An optional `verify_tools=True` and `verify_json=True` mode that runs a tiny tool-call or JSON-schema probe on newly discovered models and caches the result in the state store (tokkkie, FreeRide). Use OpenRouter `supportsToolChoice` when it is present. This addresses the provider tool-call variance documented by Exacto. (M-H, M.)
15. **Privacy filter.** `exclude_training_providers=True`, applied through OpenRouter `provider.data_collection="deny"` and a per-provider policy table (Google AI Studio outside the EU/UK, Mistral free, Kilo). Warn that on OpenRouter free models this can remove most candidates, because each has a single host. (M, L-M.)

**P2: medium value, higher cost**
16. **OpenAI-SDK-shaped facade.** `freeai.OpenAI().chat.completions.create(...)` returning OpenAI-typed objects (an optional `openai` dependency for the types). Prefer this over injecting a custom transport into the OpenAI SDK, which moved to HTTPX2. (H, M.)
17. **Optional local proxy** (`freeai serve`). `/v1/chat/completions` (JSON and SSE), `/v1/models`, served-model and attempt headers, a 127.0.0.1 bind by default, and optional bearer auth with key redaction in logs. This gives Pydantic AI, LangChain, LlamaIndex, and IDE tools compatibility through `base_url` alone. The threat surface (network exposure, key leakage) needs explicit secure defaults. (H, M-H.)
18. **OTel GenAI instrumentation** as an extra: one span per attempt with the `gen_ai.*` attributes and a `freeai.failure_class` attribute. Built on `on_attempt`. (M, L-M.)
19. **Quality tiers.** User-defined aliases (`fast`/`smart`/`coding`/`long-context`), an optional Artificial Analysis score enrichment (cached at least daily, attribution, stable IDs), and an optional LMArena dataset import. Avoid bundling learned routers (RouteLLM/RoRF): they need fixed pairs and evals, and the free pool churns on a median 75-day listing life. (M, M.)

**Avoid**
- A global `allowed_fails` count whose default is ambiguous (LiteLLM's "3 treated as unset" bug), and failure-count cooldowns that apply to a lone candidate.
- Redis round-trips on every request in the hot path when a local cache would do.
- Multi-key or multi-account rotation to evade a provider's account-level quota (OpenRouter explicitly governs capacity globally, and cheahjs asks users not to abuse these services). If key pools are supported at all, scope them to providers whose terms allow it, and document the risk.
- Silent model substitution without exposing the served model.
- Sleeping through long Retry-After values on free tiers. Cooling the candidate and moving on preserves scarce RPD.

### Gaps
- The value and cost ratings above are my inference from the cited evidence, not measured user demand. No usage telemetry or survey of freeai users was available.
- Provider terms of service on multi-key usage were not checked for Groq, Gemini, Cerebras, or the other providers.
- I did not benchmark whether pyrate-limiter's SQLite backend performs well enough for freeai's per-request path.
